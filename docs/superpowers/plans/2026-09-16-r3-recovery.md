# R3 Recovery Contracts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Establish repeatable database-backed recovery checks for durable worker scheduling and Java completion application.

**Architecture:** Exercise existing production transaction and consumer boundaries using disposable PostgreSQL databases. Inject transport or transaction failures at named boundaries; retain the real SQL and application roles. These tests establish recovery contracts; actual process termination, broker restarts and load remain separate R3 work.

**Tech Stack:** Python/pytest/psycopg and Java/JUnit/Spring JDBC/PostgreSQL; controlled Kafka transport doubles in Python tests.

**Spec:** `plan.md` sections 7, 10, 13 and 17; `AGENTS.md`; experimental R2 acceptance in `docs/evidence/2026-09-16-r2/r2-acceptance.md`.

## Global Constraints

- Java alone changes case state.
- Commit Kafka offset only after that transaction.
- A successful job is terminal.
- A stale worker cannot finalize.
- Use synthetic identities, quotes, policies, and values.
- Do not claim exactly-once transport or model billing: calls may repeat after a crash even when business effects are idempotent.
- Preserve application database ownership; fixture setup may use the migrator, tested operations use their application roles.
- Use the existing guarded `caseflow_test_<32 hex characters>` disposable database pattern; never truncate or delete demo data.
- No live AI calls, credentials in artifacts, new dependencies or cloud provisioning in this batch.
- Commit verified changes in short cohesive batches. Keep R2 extraction limitations and the USD 10 shared budget unchanged.

## Evidence boundary

Failure injection here is deterministic exceptions and real database rollbacks, not operating-system process kills. Fake Kafka acknowledgements establish consumer/publisher control-flow properties, not broker delivery or durability. The full crash matrix, 10,000 broker redeliveries, dependency restarts, query comparisons, mixed-load measurements, cloud smoke/rollback/teardown and final demo remain outside this bounded plan.

Wrap `jobs.database` to raise immediately before transaction context exit after scheduling has executed; assert zero inbox/jobs after rollback, then successful replay creates one of each. Inject an exception in `jobs.emit` during `finish`; assert RUNNING state, zero artifacts and zero success outbox rows, restore emit and replay to exactly one result/event. Establish a commit-before-offset failure by making the first controlled consumer commit raise; assert the same record is retried before any later poll and its durable job/inbox remain unique.

```python

    jobs.finish(job, artifact)

    assert db.execute("SELECT count(*) AS n FROM worker.outbox WHERE payload->>'status'='SUCCEEDED'").fetchone()["n"] == 0
```
