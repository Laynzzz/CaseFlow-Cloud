# Sustained manual document workload

This is a bounded local synthetic self-test, separate from the query-index benchmark
and live AI evaluation. Its question is whether a fixed mix of purchase reads and
manual approvals completes real documents without growing an unresolved backlog.
It does not find maximum capacity, model throughput, or cloud performance.

## Reproduce

Prerequisites: isolated `compose.release.yaml` stack, its smoke-created synthetic
identity fixtures and `infrastructure/release/generated/purchase-template.docx`,
Node 22, Docker CLI, and **k6 2.2.0**. The harness checks the installed k6 version.
Keep other release experiments out of the measurement window.

```powershell
node --test tests/load/harness.test.mjs
node tests/load/run.mjs
```

The same commands work in Linux with Node and k6 on PATH. Default endpoints are
API `127.0.0.1:18080`, Keycloak `127.0.0.1:18180`, API metrics
`127.0.0.1:18081/actuator/prometheus`, and worker metrics
`127.0.0.1:18090/metrics`. `LOAD_API_URL`, `LOAD_OIDC_ISSUER`,
`LOAD_REDIRECT_URI`, `LOAD_API_METRICS_URL`, `LOAD_WORKER_METRICS_URL`,
`LOAD_COMPOSE_PROJECT`, `LOAD_ENV_FILE`, `LOAD_TEMPLATE`, and `LOAD_OUTPUT`
override the isolated environment. All HTTP configuration accepts loopback only.

A preliminary ten-second probe can set `LOAD_WARMUP_SECONDS=0` and
`LOAD_DURATION_SECONDS=10`; label it a harness check, not sustained evidence.
The sustained defaults are 30 seconds warmup, 180 seconds measured arrivals,
2 arrivals/second and a maximum of 10 virtual users. Overrides are bounded to
0–30 seconds warmup, 10–180 seconds sustained, 1–2 arrivals/second, 1–10 users,
and 10–120 seconds drain (`LOAD_DRAIN_SECONDS`). No resets or deletions occur.

## Workload and accounting

Each run creates two tenants, each with one published two-step workflow, one
published DOCX template, and ten read-only seed drafts. Both tenants receive half
of arrivals. Deterministic fixture version `synthetic-manual-purchase-load-v1`
uses synthetic USD 4,200 laptop purchases. Seed marker 20260917 describes this
fixed fixture; no random sampling controls the mix. Tenant and case UUIDs are
generated by the application and retained in `fixtures.json`.

Eight out of each ten iterations list 20 cases and read one seeded case. The
remaining two iterations create a draft, assign manager and finance, start it,
and approve in order. These final approvals request real asynchronous DOCX jobs.
No quote, policy, extraction, review, embedding, or hosted-model calls are made.
At defaults the offered budget is 420 iterations, 336 read iterations and 84
document iterations, comprising 1,092 business HTTP requests if all complete.
Setup, authenticated bridge IPC, independent observer polling and two sample
downloads are additional traffic recorded separately from the business requests.

The single k6 `constant-arrival-rate` scenario continues through warmup and
measurement; the iteration start time supplies a static `phase` tag. Dropped
iterations stay visible and fail the run. Fixed virtual-user allocation means
the harness refuses excess work when slow responses consume all users; it does
not quietly reduce the offered rate and call that sustainable capacity. The
application timeout is 10 seconds, in-flight grace is 20 seconds, and a separate
watchdog stops a stuck generator. No URLs, case IDs, tenant IDs or user IDs are
metric labels. Operation names, phase, status and method are bounded labels.
The pinned k6 version can schedule an extra iteration at the duration boundary.
`arrival_budget_refusals` counts those offers and the harness performs no
application requests beyond the configured iteration budget. Distinguish these
budget-boundary refusals from `dropped_iterations` caused by unavailable users.

HTTP acknowledgement latency is `application_http_ack_ms`; final approval has
its own `final_approval_ack_ms`. Both sustained p95 gates are 2 seconds. No
business HTTP errors, workload errors or dropped iterations are permitted.
Bridge/observer operations are not included in these custom HTTP histograms.
Raw k6 built-in HTTP totals also contain bridge IPC, which carries `scope=harness`.

The Node observer follows every workload-created case, including cases whose
approval never completed. Every two seconds it reads document status, recording
the number completed, failed and pending. The observer makes at most ten requests
per pass and 1,200 per entire run; exhausting that budget fails the run and keeps
the unresolved backlog visible. API-visible completion latency runs
from the final approval acknowledgement until `SUCCEEDED` is observed; a second
distribution begins at final approval request start. Polling adds up to a poll
cycle plus the bounded round-robin observer delay. These values are not exact internal
worker execution times. After arrivals stop, the observer allows at most 120
seconds to drain. Failed jobs, partial approvals, missing jobs, observation errors
and unresolved cases prevent a passing result. Backlog remains in the evidence.

Worker `caseflow_job_queue_seconds` measures claim time minus `available_at`
for ready/retry jobs, or minus the prior lease expiry for reclaimed running jobs
(excluding intentional retry backoff and previous execution time). `caseflow_job_execution_seconds` measures
execution, with kind and outcome labels. Before/after cumulative histogram
snapshots must be differenced for this run; raw labels and buckets are preserved.
Missing metrics cannot substantiate queue/execution claims. Reconciliation is a
read-only worker command before and after drain with a 60-second age threshold;
it does not repair anything and does not prove the absence of younger faults.
Unhealthy or missing worker database/Kafka metric collectors fail evidence
collection. Kafka lag is the sum over partitions for the two fixed business
topic/group pairs; an unavailable group must not appear as healthy zero lag.

One successful document per tenant is downloaded after drain. The harness checks
HTTP success, metadata SHA-256 and byte size, ZIP signature, and outsider denial.
The existing release smoke parses Word contents. The load harness does not
pretend that downloading two samples independently validates all Word content.

## Evidence and interpretation

Every run, including failures, is retained under `tests/load/results/<timestamp>`:

- `environment.json`: timestamp, revision, dirty paths, exact workload source
  hashes, Node/k6/OS/CPU/memory, configuration and cache state.
- `fixtures.json`, `authorization.json`: synthetic dataset and three mandatory
  negative access checks. Missing negative fixtures never skip the checks.
- `k6-summary.json`, `k6-console.txt`: raw summary, thresholds, dropped
  iterations, errors, rates, acknowledgement latencies and generator saturation.
- `jobs.json`, `backlog.json`, `result.json`: every observed job, backlog over
  time, warmup/sustained distinction, drain and completion distributions.
- `*-worker.prom`, `*-api.prom`, `worker-histograms.json`: server metrics before,
  after warmup, midway, after arrivals and after drain, including queues/execution
  and pools. `infrastructure-snapshot-times.json` records actual collection times.
  The computed histogram delta includes warmup; the after-warmup raw snapshot
  also allows an approximate interval delta, subject to jobs spanning the boundary.
- `*-containers.jsonl`: corresponding Docker CPU/memory snapshots. Point samples
  cannot establish peak saturation; host metadata includes the generator and
  Docker Desktop resource-sharing limitation. `container-images.txt` pins the
  actual running image IDs and configured memory/CPU limits without exporting
  container environment variables.
- `*-reconciliation.json`, `sampling-errors.json`, `failure.json` when relevant:
  operational findings and failed evidence collection are kept visible.
- `downloads.json`, two `tenant-*-sample.docx` files: sampled binary evidence.

Published evidence may replace the large raw `*.prom` files with lossless
`*.prom.gz` snapshots. `raw-artifacts.json` preserves SHA-256 values of both the
original bytes and gzip archive. The measured 2026-09-17 run also includes a
normalized `workload-source.tar.gz` and per-file/source-archive hashes, so a dirty
checkout revision is not the only record of the exact executed workload.

Report completed documents per measured arrival window only alongside arrivals,
errors, latency, backlog trend, final drain and resource observations. A clean
short run is one observed operating point; it is not maximum sustainable
throughput or a latency guarantee. Seeding warms the database and templates;
there is no cache flush. Two small tenants are not the separate skewed SQL dataset.

Synthetic passwords come from the ignored release `.env`. OIDC Authorization
Code + PKCE uses the same pattern as `tests/e2e/oidc-session.mjs`; refresh tokens
keep long runs valid. Credentials and application tokens stay in memory. k6 gets
short-lived tokens through an authenticated random-port loopback bridge; no token
is written to command arguments or evidence. Ambient k6 debug/output settings are
removed so they cannot dump headers or export metrics remotely. The bridge closes
on exit. This is test machinery, not an application authentication endpoint.
